# بروتوتايب الظل المتأخر

**الهدف:** تعرف — بالتجربة على الشاشة، مش بالتفكير — إذا ميكانيك الظل ممتعة ولا لأ.

**الوقت المتوقع:** جمعتين. لو عدّت التلاتة، فيه حاجة غلط في الـ approach مش في الفكرة.

**مهم جداً:** الـ Phase دي **مش** عن الشكل. متحسّنش أي حاجة في الجرافيك، ومتضيّفش أي مرحلة جديدة، ومتلمسش الـ game feel. لو لقيت نفسك بتظبط timing الأنيميشن أو بتعدّل على المشهد، انت هربت من السؤال.

## القرار التقني الأهم: تسجّل إيه بالظبط؟

فيه طريقتين، والفرق بينهم بيحدد نص المشروع.

### الطريقة أ — تسجيل الـ Input (اللي بتتبادر للذهن)

تسجّل حالة الأزرار كل tick، وبعد `D` ثانية تشغّلها على entity تاني وتسيب الـ physics تحسب الباقي.

**المشكلة:** دي محتاجة **deterministic physics**. `update(dt)` في Flame بيجي بـ `dt` متغير كل frame (حسب الأداء)، ومعناه إن نفس تسلسل الأزرار ممكن ينتج مسار مختلف شوية. في platformer عادي مش مشكلة. في **لعبة ألغاز** فيها الظل لازم يدوس على زرار بالمليمتر، ده كارثة — اللاعب هيحل اللغز صح والظل يغلط، وهو هيلوم اللعبة (وهو محق).

فيه كومنت من لاعب على itch.io على لعبة بنفس الفكرة بيقول بالظبط: المشكلة إن الظل لما بيعيد الحركات مش بيرجع للنقطة اللي وقفت فيها بالظبط، خصوصاً في النطات، وده بيخلي الميكانيك مش نافعة. **ده الفخ المتوقع.**

### الطريقة ب — تسجيل الـ Transform (الموصى بها)

تسجّل `position` + `facing direction` + `animation state` كل fixed tick، والظل بيقرأ من الـ buffer ويحط نفسه في المكان. مفيش physics، مفيش حساب، مفيش determinism issues.

**المكسب:** الظل بيمشي **بالظبط** على نفس المسار، مضمون ١٠٠٪. وكمان لما تتعدّل الحركة في Phase 3 (سرعة، gravity، coyote time)، التسجيلات القديمة مش بتبوظ لأن اللي بيتسجّل هو النتيجة مش المدخل.

**التنازل:** الظل مش هيتفاعل مع الـ physics. لو حاجة اتحركت في البيئة بعد ما اللاعب مشي، الظل هيعدّي من خلالها. **لـ prototype دي مش مشكلة خالص** — والحل لما يحتاج إن الـ input يتسجّل كمان في نفس الـ snapshot ويُستخدم للأحداث فقط (ضغط زرار، إمساك حاجة).

**القرار: الطريقة ب.** ومتغيّرهاش من غير سبب مكتوب.

## الـ Architecture

### 1) الـ Fixed Timestep

متسجّلش كل frame. اعمل accumulator وسجّل على فاصل ثابت (مثلاً `1/60` أو `1/30` ثانية) عشان الـ buffer يبقى له معنى زمني ثابت مهما اختلف الـ FPS بين الأجهزة.

```dart
static const double tickRate = 1 / 60;
double _accumulator = 0;

@override
void update(double dt) {
  super.update(dt);
  _accumulator += dt;
  while (_accumulator >= tickRate) {
    _accumulator -= tickRate;
    _onFixedTick();
  }
}
```

### 2) الـ Snapshot

```dart
class Snapshot {
  final Vector2 position;
  final bool facingRight;
  final String animationState; // idle / walk / jump / fall
  final bool jumpPressed;      // للأحداث، مش للحركة
  const Snapshot({...});
}
```

خلّي الـ class immutable و`const` قدر الإمكان — بتتعمل منها ٦٠ في الثانية.

### 3) الـ Ring Buffer

بـ delay ٣ ثواني على ٦٠ tick = ١٨٠ snapshot في الـ buffer. حاجة تافهة في الميموري.

استخدم `Queue<Snapshot>` من `dart:collection`:
- كل fixed tick: `buffer.addLast(currentSnapshot)`
- لو `buffer.length > delayTicks`: `shadow.applySnapshot(buffer.removeFirst())`
- قبل كده الظل بيبقى مخفي (`opacity = 0` أو مش مضاف للـ tree)

الـ `Queue` عملياتها O(1) على الطرفين، فمفيش قلق على الأداء.

### 4) الـ Shadow Component

`SpriteAnimationGroupComponent` تاني، نفس الـ sprites بالظبط، بس بـ:
- `opacity` أقل (٠.٤ – ٠.٦) أو tint مختلف
- `priority` أقل من اللاعب (يرندر وراه)
- **مفيش أي منطق حركة فيه خالص** — بيستقبل snapshots وخلاص

### 5) الـ Interpolation

لو الـ FPS أعلى من الـ tick rate، الظل هيبان متقطّع. حل بسيط: خزّن آخر snapshot والـ snapshot الجاية، واعمل `Vector2.lerp` بينهم بنسبة `_accumulator / tickRate`.

**متعملهاش من أول لحظة.** شوف الأول إذا التقطيع باين فعلاً — ساعات بيبقى مقبول والـ opacity المنخفضة بتخفيه.

## الـ Debug UI — أهم جزء في الـ Phase دي

الهدف الحقيقي من الـ Phase مش كتابة الكود، الهدف **اللعب بالأرقام**. اعمل overlay فيه sliders وtoggles تتعدّل واللعبة شغالة:

| المتغير | المدى | السؤال |
|---|---|---|
| `delaySeconds` | ٠.٥ – ٦ | التأخير الصح كام؟ **متفترضش ٣.** |
| `shadowIsSolid` | on/off | الظل منصة تقف عليها ولا لأ؟ |
| `shadowKills` | on/off | الظل يقتل اللاعب لو لمسه؟ |
| `shadowOpacity` | ٠.٢ – ١ | إمتى بيبان "موجود" وإمتى بيبان "شبح"؟ |
| `showTrail` | on/off | رسم المسار المستقبلي (debug line) — بيسهّل الفهم ولا بيقتل التحدي؟ |

الأربع الأول هم اللي فعلاً هيحددوا اللعبة.

## اختبارات الجمعة — الحكم على الفكرة

اعمل **مشهد اختبار فاضي** — أرضية، منصتين، زرار، باب. **بمكعبات رمادية، مش في البيئة الحلوة.** البيئة الحلوة بتضلّل: بتخلي الإحساس إن اللعبة حلوة بسبب الجرافيك.

### التست ١ — الزرار
زرار بعيد عن الباب بمسافة تمنع الوصول للاتنين في نفس اللحظة.
**السؤال:** لما تنجح، فيه إشباع ولا ده حساب رياضي ممل؟

### التست ٢ — الظل كمنصة
منصة عالية مش توصلها بنطة واحدة. لازم اللاعب يقف في مكان معين، والظل يبقى تحته بعد التأخير، وينط فوقه.
**السؤال:** ده بيبان طبيعي ولا محتاج شرح؟ اللاعب هيكتشفه لوحده؟

### التست ٣ — الظل كعدو
شغّل `shadowKills` وامشي في ممر ضيق.
**السؤال:** ده بيخلي اللعبة متوترة وحلوة، ولا مقرفة وظالمة؟

## معيار القتل (Kill Criteria)

**لو بعد جمعتين:**

- مفيش ولا مرة حصلت لحظة "آآه" في واحد من التلات تستات →
- أو كل تست محتاج حساب رياضي في الدماغ بدل إحساس →
- أو الظل بيغلط واللاعب صح (رغم الطريقة ب) →

**الفكرة تُترك.** البيئة الجميلة الشغالة على تلات منصات مكسب حقيقي مش خسارة، وتُبنى عليها ميكانيك تانية.

**ولو حصلت لحظة "آآه" مرة واحدة بس** — كفاية. كمّل، وده سقف اللعبة اللي هتتبنى.
